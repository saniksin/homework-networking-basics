## Завдання 1. Аналіз відкритих портів

Щоб у списку був гарантований «свій» сервіс, перед перевіркою я запустив у сусідньому терміналі локальний веб-сервер:

```bash
python3 -m http.server 8080
```

### Команда

```bash
ss -tuln
```

Ключі:
* `-t` - показати TCP-сокети;
* `-u` - показати UDP-сокети;
* `-l` - тільки ті, що слухають (LISTEN для TCP, UNCONN для UDP);
* `-n` - не перетворювати номери портів на назви сервісів (`25`, а не `smtp`).

### Як читати колонки

| Колонка | Що означає |
|---|---|
| `Netid` | Транспортний протокол: `tcp` або `udp` |
| `State` | Стан сокета. `LISTEN` - TCP-сокет чекає на вхідні з'єднання. `UNCONN` (unconnected) - UDP-сокет приймає датаграми. У UDP немає з'єднань, тому стану LISTEN у нього не буває |
| `Recv-Q` / `Send-Q` | Для LISTEN-сокета: `Recv-Q` - скільки з'єднань зараз чекає в черзі на `accept()`, `Send-Q` - максимальний розмір цієї черги (backlog). Наприклад, у `python3 -m http.server` backlog = 5, у Docker = 4096 |
| `Local Address:Port` | Адреса і порт, на яких слухає сервіс |
| `Peer Address:Port` | Віддалена сторона. Для сокета, що слухає, це `0.0.0.0:*` - «будь-хто з будь-якого порту» |

На яку адресу «прив'язаний» сокет, визначає, **звідки до нього можна достукатися**:

| Адреса | Хто може підключитися |
|---|---|
| `0.0.0.0` / `[::]` | Усі IPv4 / IPv6 інтерфейси - сервіс доступний з мережі |
| `127.0.0.1` / `[::1]` | Лише loopback - тільки програми на цьому ж комп'ютері |
| `127.0.0.53%lo` | Конкретна адреса на інтерфейсі `lo` - локальний DNS-резолвер systemd-resolved |
| `10.255.255.254` | Службова адреса WSL на `lo` - DNS-проксі WSL, який пересилає запити у Windows |
| `224.0.0.251` | Multicast-група mDNS (приймає групові розсилки в локальній мережі) |

### Відкриті порти

| № | Протокол | Порт | Адреса | Стан | Сервіс |
|---|---|---|---|---|---|
| 1 | **TCP** | **8080** | `0.0.0.0` | **LISTEN** | HTTP - мій тестовий веб-сервер `python3 -m http.server` |
| 2 | **TCP** | **25** | `0.0.0.0`, `[::]` | **LISTEN** | SMTP - поштовий сервер Postfix (приймає пошту) |
| 3 | **TCP** | **53** | `127.0.0.53`, `10.255.255.254` | **LISTEN** | DNS - локальний резолвер systemd-resolved і DNS-проксі WSL (TCP використовується для великих DNS-відповідей) |
| 4 | **UDP** | **53** | `127.0.0.53`, `10.255.255.254` | **UNCONN** | DNS - ті самі служби. Звичайні DNS-запити йдуть саме через UDP |
| 5 | **UDP** | **5353** | `224.0.0.251` | **UNCONN** | mDNS (Multicast DNS) - пошук пристроїв у локальній мережі (`*.local`, Chromecast, принтери). Відкрив браузер Chrome |
| 6 | **TCP** | **8081, 8082, 8420** | `0.0.0.0`, `[::]` | **LISTEN** | Порти, прокинуті з Docker-контейнерів на хост (`docker run -p`) |
| 7 | **TCP** | **39271, 19834, …** | `127.0.0.1` | **LISTEN** | Високі динамічні порти, доступні лише локально. Їх відкриває VS Code Server (розширення, мовні сервери) |

У форматі зразка:

```
TCP порт: 8080 → HTTP (python3 -m http.server)        Стан: LISTEN
TCP порт: 25   → SMTP (поштовий сервер Postfix)        Стан: LISTEN
TCP порт: 53   → DNS (systemd-resolved / DNS-проксі WSL)   Стан: LISTEN
UDP порт: 53   → DNS (systemd-resolved / DNS-проксі WSL)   Стан: UNCONN
UDP порт: 5353 → mDNS (браузер Chrome)                 Стан: UNCONN
```

### Висновок до завдання 1

У системі відкрито багато портів, але приймати з'єднання з мережі (прив'язані до `0.0.0.0` / `[::]`) можуть лише TCP 8080, 25, 8081, 8082, 8420. Оскільки це WSL за NAT, «з мережі» тут фактично означає з Windows-хоста. З домашньої мережі чи інтернету ці порти напряму недоступні без додаткового прокидання. Решта слухає на `127.0.0.1` / `127.0.0.53` і доступна тільки з цього ж комп'ютера. Добре видно різницю між протоколами: TCP-сокети мають стан `LISTEN`, бо чекають на встановлення з'єднання, а UDP-сокети мають стан `UNCONN`, бо UDP не встановлює з'єднань і просто приймає датаграми. Один і той самий порт 53 відкрито двічі, окремо для TCP і для UDP: для ядра це два незалежні сокети.

### Перевірка через `ps`

Щоб переконатися, що PID з `ss` справді відповідають цим програмам, перевірив їх через `ps`:

```bash
ps -o pid,comm,args -p 302,368,1095,1803,2315278
```

```
    PID COMMAND         COMMAND
    302 systemd-resolve /lib/systemd/systemd-resolved
    368 containerd      /usr/bin/containerd
   1095 master          /usr/lib/postfix/sbin/master -w
   1803 docker-proxy    /usr/bin/docker-proxy -proto tcp -host-ip 0.0.0.0 -host-port 8081 ...
2315278 python3         python3 -m http.server 8080
```

* Ім'я `systemd-resolve` у `ss` обрізане до 15 символів: так ядро зберігає ім'я процесу (`comm`). Повна назва - `systemd-resolved`.
* `MainThread` - це не назва програми, а ім'я потоку процесу Node.js. Через `ps` видно, що це процеси `~/.vscode-server/.../node` (VS Code Server).

### Що лишилося без процесу навіть із `sudo`

Рядки `10.255.255.254:53` та `127.0.0.1:323` / `[::1]:323` без імені процесу. Я перевірив це детальніше:

```bash
sudo ss -ulpne 'sport = :323 or sport = :53'
```
```
UNCONN 0 0  127.0.0.53%lo:53  0.0.0.0:*  users:(("systemd-resolve",pid=302,fd=13)) uid:101 ino:384 sk:169 cgroup:/system.slice/systemd-resolved.service <->
UNCONN 0 0 10.255.255.254:53  0.0.0.0:*  ino:128 sk:16a cgroup:/ <->
UNCONN 0 0      127.0.0.1:323 0.0.0.0:*  ino:21512 sk:16b cgroup:/ <->
UNCONN 0 0          [::1]:323    [::]:*  ino:21513 sk:16c cgroup:/ v6only:1 <->
```

Для `systemd-resolved` видно службу (`cgroup:/system.slice/systemd-resolved.service`). Решта три сокети лежать у кореневій cgroup (`cgroup:/`), без жодної служби systemd. Пошук їхніх inode (`128`, `21512`) у `/proc/*/fd` теж нічого не знайшов: жоден процес, видимий в Ubuntu, їх не тримає. Отже, їх створює сама інфраструктура WSL, яка працює поза процесами дистрибутиву (DNS-проксі WSL на `10.255.255.254:53`). Порт 323 - стандартний командний порт служби часу chrony, але самого `chronyd` у дистрибутиві немає, тож це теж службовий сокет WSL. `ss` бачить сокет, але не може зіставити його з жодним PID.

### Висновок до завдання 2

Команда `ss -tulpn` дозволяє зв'язати порт із конкретною програмою. Без `sudo` видно лише сокети власних процесів, а системні служби, що працюють від інших користувачів (`root` для Postfix і Docker, `systemd-resolve` для DNS-резолвера), показуються без імені. Це захист: звичайний користувач не повинен бачити деталі чужих процесів. З `sudo` видно всі процеси: `python3` (PID 2315278) слухає TCP 8080, Postfix `master` (PID 1095) слухає TCP 25, `systemd-resolved` (PID 302) слухає TCP і UDP 53. Знаючи PID, можна подивитися деталі процесу (`ps`, `/proc/<PID>`) або зупинити його (`kill <PID>`), якщо порт треба звільнити.

## Завдання 3. Перевірка TCP-з'єднання

### Команда (netcat)

```bash
nc -vz google.com 80
```

Ключі:
* `-v` (verbose) - вивести результат перевірки;
* `-z` (zero-I/O) - лише перевірити, чи порт відкритий: встановити з'єднання і одразу закрити, не передаючи даних.

### Результат

```
Connection to google.com (142.251.98.100) 80 port [tcp/http] succeeded!
```

Код завершення команди `echo $?` = `0` (успіх).

### Команда (telnet)

Для порівняння виконав і другий варіант:

```bash
telnet google.com 80
```

```
Trying 142.250.130.100...
Connected to google.com.
Escape character is '^]'.
Connection closed by foreign host.
```

`Trying …` - telnet отримав IP-адресу через DNS і надсилає SYN. `Connected to google.com.` - TCP-з'єднання встановлено. Після цього я ввів `quit`, а це не коректний HTTP-запит. Тому веб-сервер Google нічого не відповів і сам закрив з'єднання (`Connection closed by foreign host`). Це теж підтверджує, що TCP-сесія існувала: закрити можна лише встановлене з'єднання.

Різні IP-адреси (`142.251.98.100` у `nc` та `142.250.130.100` у `telnet`) - це нормально: у Google багато серверів, і DNS щоразу може повернути іншу адресу (балансування навантаження).

### Що відбувається «під капотом»

`nc -vz` повідомляє `succeeded` лише тоді, коли повністю пройшло **трикрокове рукостискання TCP (3-way handshake)**:

```
Мій ПК                                  google.com:80
  | ---- SYN (хочу з'єднатися) ---------> |
  | <--- SYN-ACK (згоден, підтверджую) --- |
  | ---- ACK (підтверджую) --------------> |   ← з'єднання ESTABLISHED, nc пише "succeeded"
  | ---- FIN (закриваю, бо -z) ----------> |
  | <--- FIN-ACK ------------------------- |
```

Реальний обмін такими пакетами я зафіксував за допомогою `tcpdump` у завданні 4 (там видно прапорці `[S]`, `[S.]`, `[.]`, `[F.]`).

### Підсумок

```
Connection to google.com (142.251.98.100) 80 port [tcp/http] succeeded!

Тип з'єднання: TCP
Порт: 80 (HTTP), [tcp/http] - назва сервісу з /etc/services
Результат: з'єднання встановлено (SYN → SYN-ACK → ACK пройшли успішно)
```

### Висновок до завдання 3

TCP-з'єднання з `google.com` на порт 80 успішно встановлюється. Це означає, що одночасно працюють DNS (ім'я перетворилося на IP), маршрутизація і NAT (пакети дійшли до Google і повернулися), а на сервері порт 80 відкритий і на ньому є сервіс. Оскільки TCP орієнтований на з'єднання, `nc` може точно сказати «відкрито» чи «закрито»: якщо сервер відповів SYN-ACK, порт відкритий; якщо відповів RST - закритий; якщо мовчить - пакети фільтрує брандмауер.

## Завдання 4. Порівняння TCP vs UDP

### Команди та результати

```bash
nc -u -vz 8.8.8.8 53
```

```
Connection to 8.8.8.8 53 port [udp/domain] succeeded!
```

```bash
nc -vz 8.8.8.8 53
```

```
Connection to 8.8.8.8 53 port [tcp/domain] succeeded!
```

На перший погляд результат однаковий: обидва `succeeded`. Але значення цього слова для TCP і UDP **зовсім різне**. Щоб це довести, я провів кілька додаткових перевірок.

### Перевірка 1. Що реально йде по мережі (`tcpdump`)

Під час обох команд я записував трафік на інтерфейсі `eth0`:

```bash
sudo tcpdump -i eth0 -nn 'host 8.8.8.8 and port 53'
```


**TCP (6 пакетів, обмін в обидві сторони):**

| Пакет | Прапорці | Значення |
|---|---|---|
| 1. ПК → 8.8.8.8 | `[S]` SYN | Запит на з'єднання, мій випадковий початковий номер `seq 813880990` |
| 2. 8.8.8.8 → ПК | `[S.]` SYN-ACK | Сервер погоджується: `ack 813880991` (мій seq + 1) і свій `seq 3163992040` |
| 3. ПК → 8.8.8.8 | `[.]` ACK | Я підтверджую. **З'єднання встановлено** - саме тут `nc` пише `succeeded` |
| 4. ПК → 8.8.8.8 | `[F.]` FIN | `nc -z` одразу закриває з'єднання |
| 5. 8.8.8.8 → ПК | `[F.]` FIN-ACK | Сервер теж закриває свою сторону |
| 6. ПК → 8.8.8.8 | `[.]` ACK | Останнє підтвердження, з'єднання закрито коректно |

Також видно, як сторони домовляються про параметри сесії: розмір сегмента (`mss 1460` / `mss 1412`), вікно (`win`, `wscale`), підтримку вибіркових підтверджень (`sackOK`). Між SYN і SYN-ACK пройшло ~27 мс - це час «туди і назад» (RTT) до сервера Google.

**UDP (4 пакети, тільки в один бік):**

* `nc -u -z` надсилає датаграми з 1 байтом даних (символ `X`). tcpdump позначає їх `(invalid)`, бо 1 байт - некоректний DNS-запит (мінімальний заголовок DNS - 12 байт).
* Від 8.8.8.8 **не прийшло жодної відповіді**: сервер не зрозумів «запит» і просто проігнорував його.
* Попри це `nc` написав `succeeded`. Для UDP це означає лише «я відправив дані й **не отримав повідомлення про помилку**», а не «сервер відповів».

### Перевірка 2. Контрольний порт, на якому нічого немає

Щоб показати, що UDP-«успіх» нічого не гарантує, перевірив порт 54, на якому в Google немає жодного сервісу:

```bash
nc -u -vz 8.8.8.8 54
```
```
Connection to 8.8.8.8 54 port [udp/*] succeeded!
```

```bash
nc -vz 8.8.8.8 54
```
```
nc: connect to 8.8.8.8 port 54 (tcp) timed out: Operation now in progress
```

* **UDP** знову каже `succeeded`, хоча сервісу на порту 54 немає. Брандмауер Google мовчки відкидає пакет, помилка не повертається, і `nc` трактує мовчання як успіх. Це **хибнопозитивний** результат.
* **TCP** чесно повідомляє про проблему: SYN відправлено, але SYN-ACK так і не прийшов, тому таймаут. Отже, з'єднання **не** встановлено.

### Перевірка 3. Закритий порт на власному комп'ютері

```bash
nc -vz 127.0.0.1 9999
```
```
nc: connect to 127.0.0.1 port 9999 (tcp) failed: Connection refused
```

```bash
nc -u -vz 127.0.0.1 9999
```
```
(вивід порожній, код завершення 1)
```

Що при цьому йде по інтерфейсу `lo` для UDP:

```bash
sudo tcpdump -i lo -nn 'udp port 9999 or icmp'
```
```
21:21:22.815383 IP 127.0.0.1.55938 > 127.0.0.1.9999: UDP, length 1
21:21:22.815391 IP 127.0.0.1 > 127.0.0.1: ICMP 127.0.0.1 udp port 9999 unreachable, length 37
```

* **TCP:** ядро одразу відповідає пакетом `RST`, і `nc` пише `Connection refused` - порт точно закритий.
* **UDP:** у відповідь на датаграму ядро надсилає ICMP-повідомлення `udp port 9999 unreachable` (видно в tcpdump вище). `nc` його отримує і не пише `succeeded` (код завершення 1). Тобто UDP-перевірка може виявити закритий порт **тільки** якщо віддалена сторона чесно повертає ICMP-помилку. Багато серверів в інтернеті її не надсилають або брандмауер її блокує, як у перевірці 2.

### Перевірка 4. Справжній DNS-запит через UDP і через TCP

Щоб перевірити, що DNS-сервіс справді відповідає по обох протоколах, надіслав коректний DNS-запит за допомогою `dig`:

```bash
dig @8.8.8.8 github.com +noall +answer +stats
```
```
github.com.		60	IN	A	140.82.121.3
;; Query time: 21 msec
;; SERVER: 8.8.8.8#53(8.8.8.8) (UDP)
;; MSG SIZE  rcvd: 55
```

```bash
dig +tcp @8.8.8.8 github.com +noall +answer +stats
```
```
github.com.		60	IN	A	140.82.121.3
;; Query time: 43 msec
;; SERVER: 8.8.8.8#53(8.8.8.8) (TCP)
;; MSG SIZE  rcvd: 55
```

Відповідь однакова, але **через TCP запит удвічі повільніший (43 мс проти 21 мс)**. Через UDP достатньо одного обміну «запит → відповідь» (1 RTT). Через TCP спочатку потрібне рукостискання SYN / SYN-ACK / ACK (ще 1 RTT), і лише потім передача даних. Саме тому DNS за замовчуванням працює через UDP, а TCP використовує лише для великих відповідей (понад 512 байт / ліміт EDNS) та передачі зон між серверами.

### Порівняльна таблиця

| Критерій | TCP (`nc -vz 8.8.8.8 53`) | UDP (`nc -u -vz 8.8.8.8 53`) |
|---|---|---|
| Результат `nc` | `succeeded` | `succeeded` |
| Що насправді означає `succeeded` | Сервер відповів SYN-ACK, з'єднання встановлено | Дані відправлено, повідомлення про помилку не прийшло |
| Пакетів у мережі | 6, в обидві сторони | 4, тільки від мене |
| Відповідь від сервера | Є (SYN-ACK, FIN-ACK) | Немає |
| Встановлення сесії | Так, 3-way handshake | Ні, connectionless |
| Закриття сесії | Так, FIN / FIN-ACK / ACK | Немає чого закривати |
| Порт без сервісу (54) | `timed out` - правдиво | `succeeded` - хибнопозитивно |
| Закритий локальний порт | `Connection refused` (RST) | Тиха помилка (ICMP Port Unreachable) |
| Гарантія доставки | Так (seq / ack, повторна передача) | Ні |
| Швидкість (реальний DNS-запит) | 43 мс | 21 мс |
| Надійність перевірки через `nc` | Висока | Низька |

### Висновок до завдання 4

**TCP:** є підтвердження з'єднання. Перед передачею даних TCP встановлює сесію за допомогою трикрокового рукостискання, нумерує байти (`seq`/`ack`) і підтверджує отримання, а наприкінці коректно закриває сесію. Тому `nc` для TCP дає точну відповідь: порт відкритий (SYN-ACK), закритий (RST) або фільтрується (таймаут).

**UDP:** немає гарантії відповіді. UDP не встановлює з'єднання і не підтверджує доставку: датаграма просто відправляється. Тому `nc -u` не може довести, що порт відкритий. Він лише фіксує, що не отримав ICMP-помилку. Це я показав на порту 54: UDP «succeeded», хоча сервісу там немає, тоді як TCP чесно повідомив про таймаут. Перевірити UDP-сервіс можна тільки протокольним запитом, на який сервіс має відповісти (для DNS це `dig`).

**Різниця:** TCP встановлює сесію і гарантує доставку ціною додаткового часу на рукостискання. UDP не встановлює сесію, працює швидше (1 RTT замість 2), але надійність і перевірку відповіді має забезпечувати сама програма.

## Завдання 5. DNS-резолвінг

Замість `google.com` використав домен **`github.com`**.

### Команда 1: `nslookup`

```bash
nslookup github.com
```

```
Server:		10.255.255.254
Address:	10.255.255.254#53

Non-authoritative answer:
Name:	github.com
Address: 140.82.121.4
```

* `Server` / `Address` - DNS-сервер, якому було надіслано запит, і порт `#53`.
* `Non-authoritative answer` - відповідь **не авторитетна**: її дав не DNS-сервер, відповідальний за зону `github.com`, а рекурсивний резолвер, який узяв запис зі свого кешу або сам дізнався його в авторитетного сервера.

### Команда 2: `dig`

```bash
dig github.com
```

```
; <<>> DiG 9.18.39-0ubuntu0.22.04.7-Ubuntu <<>> github.com
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 51489
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 1232
;; QUESTION SECTION:
;github.com.			IN	A

;; ANSWER SECTION:
github.com.		20	IN	A	140.82.121.3

;; Query time: 10 msec
;; SERVER: 10.255.255.254#53(10.255.255.254) (UDP)
;; WHEN: Sat Oct 31 21:17:59 UTC 2026
;; MSG SIZE  rcvd: 55
```

### Розбір відповіді `dig`

| Рядок | Значення |
|---|---|
| `status: NOERROR` | Запит виконано успішно, домен існує (для неіснуючого було б `NXDOMAIN`) |
| `flags: qr rd ra` | `qr` - це відповідь (query response); `rd` - я попросив рекурсивний пошук (recursion desired); `ra` - сервер підтримує рекурсію (recursion available). Прапорця `aa` (authoritative answer) немає, тому відповідь неавторитетна, як і писав `nslookup` |
| `QUESTION SECTION: github.com. IN A` | Що питали: запис типу `A` (IPv4-адреса) для `github.com`, клас `IN` (Internet) |
| `ANSWER SECTION: github.com. 20 IN A 140.82.121.3` | Відповідь: IPv4-адреса **140.82.121.3**, `20` - TTL, тобто скільки секунд запис ще можна зберігати в кеші |
| `EDNS … udp: 1232` | Розширення DNS: клієнт готовий приймати UDP-відповіді до 1232 байт. Якщо відповідь більша, запит буде повторено через TCP |
| `Query time: 10 msec` | Час отримання відповіді |
| `SERVER: 10.255.255.254#53 (UDP)` | **DNS-сервер, який відповів**, порт 53, протокол UDP |
| `MSG SIZE rcvd: 55` | Розмір відповіді - 55 байт, тому вистачило однієї UDP-датаграми |

### Чому `nslookup` дав `.4`, а `dig` - `.3`?

У `github.com` кілька IP-адрес у мережі `140.82.121.0/24`, і DNS по черзі повертає різні з них (**round-robin DNS**). Так навантаження розподіляється між серверами. TTL лише 60 секунд саме для того, щоб GitHub міг швидко перемикати трафік між серверами.

### Звідки береться DNS-сервер `10.255.255.254`

```bash
cat /etc/resolv.conf
```
```
nameserver 10.255.255.254
search home
```

```bash
resolvectl status
```
```
Global
         Protocols: -LLMNR -mDNS -DNSOverTLS DNSSEC=no/unsupported
  resolv.conf mode: foreign
Current DNS Server: 10.255.255.254
       DNS Servers: 10.255.255.254
        DNS Domain: home
```

`10.255.255.254` - це **DNS-проксі WSL** (той самий сокет `10.255.255.254:53`, який ми бачили в `ss` у завданнях 1-2). WSL автоматично записує його в `/etc/resolv.conf`. Проксі приймає запит від Linux і передає його DNS-клієнту Windows, а той пересилає запит DNS-серверам, налаштованим у Windows (`1.1.1.1` і `8.8.8.8` з `ipconfig /all` у ДЗ №1). Ланцюжок виглядає так:

```
dig (Ubuntu) → 10.255.255.254:53 (DNS-проксі WSL) → DNS-клієнт Windows → 1.1.1.1 / 8.8.8.8 → ... → авторитетні сервери github.com
```

Для порівняння я запитав публічний DNS Google напряму (див. також завдання 4):

```bash
dig @8.8.8.8 github.com +noall +answer +stats
```
```
github.com.		60	IN	A	140.82.121.3
;; Query time: 21 msec
;; SERVER: 8.8.8.8#53(8.8.8.8) (UDP)
```

Тут сервер, що відповів, уже `8.8.8.8`. TTL = 60: це «свіжий» запис. У локальному ланцюжку TTL був 20, бо запис уже приблизно 40 секунд (60 - 20) лежав у кеші резолвера і його «залишок життя» зменшився.

### Підсумок

```
Домен: github.com
IP: 140.82.121.3 (dig) / 140.82.121.4 (nslookup) - кілька адрес, round-robin
Тип запису: A (IPv4), TTL 20-60 с
DNS сервер: 10.255.255.254 (DNS-проксі WSL, порт 53, протокол UDP)
            → далі пересилає на DNS Windows: 1.1.1.1 / 8.8.8.8
Тип відповіді: неавторитетна (non-authoritative, немає прапорця aa)
```

### Висновок до завдання 5

DNS перетворює доменне ім'я на IP-адресу: для `github.com` повернуто адреси `140.82.121.3` / `140.82.121.4`. Відповідь надав DNS-сервер `10.255.255.254`. Це проксі WSL, який пересилає запити DNS-серверам Windows. Відповідь неавторитетна, бо прийшла від рекурсивного резолвера з кешем, а не від сервера, відповідального за зону `github.com`. Запит і відповідь пройшли через **UDP-порт 53**, і це пов'язує завдання 5 із завданням 4: DNS - класичний приклад служби, якій важлива швидкість одного обміну «запит-відповідь», тому за замовчуванням вона використовує UDP.

## Загальний підсумок: зв'язок з моделями OSI та TCP/IP

| Що досліджували | Рівень OSI | Рівень TCP/IP |
|---|---|---|
| Порти, сокети, стани `LISTEN` / `UNCONN` (`ss`) | L4 - транспортний | Транспортний |
| TCP: рукостискання, `seq`/`ack`, FIN; UDP: датаграми без підтвердження (`nc`, `tcpdump`) | L4 - транспортний | Транспортний |
| ICMP Port Unreachable при закритому UDP-порту | L3 - мережевий | Міжмережевий (Internet) |
| Процеси, що відкривають сокети (`ss -p`, PID) | L7 - програми, які користуються транспортним рівнем | Прикладний |
| DNS (`nslookup`, `dig`), HTTP (порт 80), SMTP (порт 25), mDNS | L7 - прикладний | Прикладний |
